# `refineforge-studio` — production GUI enterprise build plan

> **Status:** PLAN ONLY. No code in this commit. Plan is intended
> to be costed, scoped, and reviewed BEFORE any of phases 0-8
> below are executed. Honest estimate: **~13-14 calendar weeks
> (~3 months)** for one experienced Rust + Tauri + frontend
> engineer working 80% on this project.

## 1. Goal

Build `refineforge-studio`, a **professional, production-ready
desktop GUI** that exposes the four refineforge sections (Lean
Specialist, ML Engineer, DevOps, CUDA Engineer) plus the
cross-cutting operator console (escalation queue + autonomous
driver) to operators who want a visual workflow over the CLI.

**Success criterion (acceptance gate for the whole project):**
three operators new to refineforge complete a five-step task
end-to-end **without help and without the CLI**:
1. Browse the claim registry, open EXAMPLE-002.
2. See the refinement-doc + Rust source + Lean theorem
   side-by-side.
3. Trigger `refine autonomous EXAMPLE-002 --strategy anthropic
   --auto-repair` from a button; watch progress stream.
4. Review the Cat 2 packet generated by the LLM; approve it
   with a reason; see the commit happen in real time.
5. View the sealed bundle's SHA-256 manifest + Sigstore
   signature; export the bundle to a chosen directory.

Time-to-completion target per operator: **under 5 minutes
excluding Lake build time.** Measured in a recorded UX session;
not self-reported.

The GUI does **NOT** replace the CLI. The CLI remains canonical;
the GUI is an opinionated productivity surface. Every action
the GUI performs can be expressed as a sequence of CLI
invocations + git operations, documented per-screen so power
users know what's happening under the hood.

Why this order:
- **Operator value first** (Phases 2-3) because the escalation
  queue is the single highest-ROI UI surface. Every other
  capability has a CLI; the queue dashboard is genuinely
  new value.
- **Read-only before write** (Phase 2 before 3) because the
  read-only views have zero blast-radius and let the team
  validate the IPC bridge + design system before any
  destructive action is wired.
- **Section 1 before 2/3/4** because Section 1 is the heaviest
  click-path (claim browsing + Lean diagnostic display) and
  its widgets (file tree, diff viewer, term renderer) are
  reused by the other sections.
- **Accessibility + packaging last** (Phase 8) because both
  are cross-cutting and tend to slip when done mid-build;
  reserving a dedicated phase avoids the trap of "we'll add
  a11y after we ship."

## 3. Phase-by-phase

### Phase 0 — Design + UX research + threat model

- **Deliverables:**
  - Figma file with the 5-screen task flow mocked end-to-end.
  - Design system (colors, typography, spacing, motion) keyed
    to Radix UI primitives so we get a11y + RTL for free.
  - Threat model doc `docs/security-gui.md`: what new attack
    surface the GUI introduces, what it inherits from the CLI,
    what's out of scope.
  - Accessibility audit plan (WCAG 2.1 AA criteria to test).
- **Time:** 1 week.
- **Acceptance:**
  - Operator (you) signs off on the 5-screen flow as the
    canonical task.
  - Threat model is reviewed against criteria v0.3 — the GUI
    binary becomes a Cat 8 (trust-base) artifact; any
    dependency on it from existing claims trips Cat 8.
- **Risks:**
  - Visual scope creep: every additional screen costs ~1 week.
    Mitigation: lock the 5-screen task flow as the v1 surface;
    everything else is v1.1+.

### Phase 1 — Tauri scaffold + IPC bridge

- **Goal:** A `refineforge-studio` workspace crate that opens
  a window, displays a placeholder, and exposes Rust commands
  to the frontend via Tauri's IPC.
- **Scope:**
  - New workspace crate `crates/refineforge-studio/`.
  - Tauri 2.x backend. Single window with system menu.
  - Frontend in TypeScript (Solid + Vite + Tailwind + Radix UI
    + Heroicons). Solid chosen for reactivity-without-VDOM
    + smaller bundle vs React.
  - IPC commands (`#[tauri::command]`): `claims_list`,
    `claim_load`, `escalations_list`, `autonomous_runs_list`.
    Each wraps the corresponding existing `refineforge-cli`
    library function.
  - State management via Solid stores; no Redux/Zustand.
  - Frontend build pipeline: `pnpm` → Vite → Tauri bundle.
- **Tests:**
  - Rust unit tests on the IPC command wrappers (no UI dep).
  - Playwright e2e: window opens, placeholder renders.
  - Manual: cross-platform open (Windows + macOS + Linux).
- **Time:** 1 week.
- **Acceptance:**
  - `cargo run -p refineforge-studio` opens a window with
    "Hello refineforge" + a working `claims_list` IPC call
    that returns real EXAMPLE-* data.
  - Frontend hot-reload works under `tauri dev`.
- **Risks:**
  - Tauri 2.x API churn — mitigation: pin Tauri minor version.
  - WebView2 dependency on Windows — mitigation: Tauri's
    installer handles it; document the runtime requirement.

### Phase 2 — Read-only views (operator-first)

- **Goal:** The operator can browse claims, see the escalation
  queue, and inspect run reports — all without typing.
- **Scope:**
  - **Claim browser** (`/claims`): list view with status badges
    (verified/drafted/broken), filterable. Click into detail
    page showing the YAML pretty-printed + the Lean theorem
    list + (if present) the refinement doc rendered as markdown.
  - **Escalation queue** (`/escalations`): mirrors `refine
    escalations list` output with row-level PENDING/DECIDED
    indicators, age column, claim filter. Click a row to view
    the full packet markdown + decision section + any operator
    notes.
  - **Run-report viewer** (`/runs`): list of `autonomous/runs/*.json`,
    click-through to a per-run detail page showing every step
    outcome, cost spend, Anthropic UsageStats (token counts +
    `stop_reasons`), elapsed timings as a Gantt-style bar chart.
  - **Bundle inspector** (`/bundles`): list of `artifacts/*/`,
    click-through showing manifest.json file tree, per-file
    SHA-256, and "Verify" button (calls `refine bundle verify`
    via IPC).
- **Tests:**
  - Component unit tests via Vitest.
  - IPC integration tests against the real refineforge repo
    fixtures.
  - Visual regression via Playwright screenshot diffs (no
    pixel-perfect; semantic-equivalent threshold).
- **Time:** 2 weeks.
- **Acceptance:**
  - Operator can navigate the four read-only screens entirely
    via keyboard.
  - Every screen has a "View as CLI command" toggle that
    shows the equivalent `refine ...` invocation (this is the
    "GUI is opinionated, CLI is canonical" contract made
    explicit).
- **Risks:**
  - Markdown rendering for refinement docs needs Lean code
    fence support — use Shiki or Highlight.js with a Lean
    grammar file.

### Phase 3 — Operator console: write actions

- **Goal:** The operator can approve/reject escalation packets
  + launch autonomous runs + see them stream live.
- **Scope:**
  - **Packet approval UI:** in the escalation detail view,
    show a form with three radio buttons (Approve / Reject /
    Edit-and-Resubmit) + a reason textarea + a partial-form
    section for batched packets. On submit, IPC command
    rewrites the packet markdown, runs `git add` + `git
    commit`, refreshes the queue.
  - **Autonomous launcher** (`/autonomous/new`): form picking
    a claim, a strategy, `--max-cost-usd`, and optional
    injection flags. **Cost preview** shows the upfront-estimate
    based on `--auto-repair` + max-iterations × `$0.07/attempt`.
    "Dry-run first" is the default + recommended.
  - **Live run streaming:** when `refine autonomous` runs from
    the GUI, the backend spawns the binary as a child process,
    captures stdout line-by-line, parses the structured
    `--json-output` format (new CLI feature — to be added in
    `refineforge-cli` as a small Phase 3 sub-task), and pushes
    events to the frontend via Tauri's event channel. Frontend
    renders steps as they happen: status icons flip from ⏳
    to ✅/❌, cost bar updates, LLM token counts stream live.
  - **Cancel button:** the run can be cancelled from the GUI;
    the spawned process gets SIGTERM (or `taskkill /t /pid`
    on Windows).
- **Tests:**
  - Mock-backed approval flow tests (Vitest + Tauri mock
    plugins).
  - Integration test: real `refine autonomous` against
    EXAMPLE-001 with `--strategy mock` — assert stream events
    arrive in the right order + the final outcome matches the
    CLI's stdout.
- **Time:** 2 weeks.
- **Acceptance:**
  - The Phase 4 acceptance test (5-step task flow) succeeds
    end-to-end against EXAMPLE-002 with `--strategy
    anthropic-mock`.
  - Live LLM streaming works against real Anthropic (operator
    runs a $1-cap demo to confirm).
- **Risks:**
  - Process management on Windows is finicky — mitigation:
    use `tokio::process::Command` consistently; document the
    Windows-specific kill semantics.
  - The `--json-output` CLI extension for streaming events is
    a separate cross-cutting change in `refineforge-cli` —
    not a GUI risk per se but the GUI can't ship without it.

### Phase 4 — Section 1 dashboard (Lean Specialist)

- **Goal:** Make the Lean side legible. The operator sees what
  theorems exist, which compile, what the policy gate caught,
  and what the bundle ships.
- **Scope:**
  - Claim detail (extended from Phase 2): Lean diagnostic
    panel showing `lake build` output structured per file
    + per theorem.
  - Policy gate panel: per-claim list of sorries / admits /
    non-core axioms found, with file:line links to the source.
  - Scaffolding wizard (`/new-claim`): wraps `refine new` with
    a multi-step form (template picker → module path validator
    → claim id generator → preview → create). NO authoring
    of Lean code in the GUI; the wizard writes the template,
    opens the file in the operator's chosen editor (configurable
    in settings).
  - Bundle inspector (Phase 2's stub, fleshed out): file tree,
    per-file SHA-256 with copy-to-clipboard, side-by-side diff
    against a previous bundle if multiple exist for the same
    claim.
- **Time:** 2 weeks.
- **Acceptance:**
  - Operator can scaffold a new claim via the wizard end-to-end
    + see it appear in the claim browser with status `drafted`.
  - Lean diagnostic panel correctly renders errors when the
    claim is broken (test with the AUTON-LIVE-002 broken-rfl
    fixture from the Phase 4 audit).

### Phase 5 — Section 2 dashboard (ML Engineer)

- **Goal:** Repair-loop visibility + eval orchestration +
  training-experiment monitoring.
- **Scope:**
  - **Repair-loop monitor** (`/repair/:claim_id`): live per-
    iteration diagnostic, AI proposed patch with syntax
    highlighting, patch-applied diff, accept/reject status.
    For Anthropic strategy: cost spend + token counts streamed
    per iteration.
  - **Eval-corpus runner** (`/eval`): trigger `refine-eval
    --corpus <jsonl> --strategy <s>` from the GUI; visualize
    repair-rate, latency percentiles, per-entry outcome
    breakdown.
  - **Training-experiment dashboard** (`/training`): trigger
    `refine-train run <yaml>` from the GUI; live progress
    chart pulled from `progress.jsonl`; checkpoint timeline;
    failure-classifier breakdown.
- **Time:** 2 weeks.
- **Acceptance:**
  - Eval run against the 3-entry tutorial corpus completes
    in the GUI + matches the CLI's JSON report exactly.
  - Training stub-script run renders progress accurately
    (no real GPU needed for this acceptance).

### Phase 6 — Section 3 dashboard (DevOps)

- **Goal:** Make the supply-chain story visible.
- **Scope:**
  - Bundle signing status: per-bundle indicator of whether a
    Sigstore signature exists in `artifacts/<id>/manifest.json.sigbundle`;
    if present, decoded cert identity + OIDC issuer + Rekor
    log entry link.
  - Release-ritual launcher: GUI wrapper around `release/release.sh`
    with the 12 steps as a checklist. Dry-run is default;
    real run requires explicit confirmation.
  - Signature verification panel: drag-and-drop a bundle dir,
    GUI runs `refine bundle verify --verify-signature`,
    displays the identity / issuer / Rekor entry; clearly
    distinguishes "hashes valid, signature valid" from
    "hashes valid, signature missing" from "hashes invalid."
- **Time:** 1.5 weeks.
- **Acceptance:**
  - Verification panel correctly handles all three cases above
    against test fixtures.
  - Release-ritual dry-run UI matches the script's output line
    for line.

### Phase 7 — Section 4 dashboard (CUDA Engineer)

- **Goal:** Bit-exact gate visibility.
- **Scope:**
  - Kernel registry view: list of `kernels/configs/*.yaml`,
    each row showing last-run hash count + Pass/Fail.
  - Gate runner: trigger `refine-bitexact run <kernel.yaml>`
    from the GUI; live N-run progress; SHA-256 histogram per
    run showing convergence / divergence.
  - Baseline diff viewer: when a kernel's hash set changes
    between runs, show a clear diff with "REGRESSION DETECTED"
    or "BASELINE UPDATED" badges. Operator approves baseline
    updates explicitly.
  - Hardware-class metadata: per-run record of GPU model,
    CUDA toolkit version, nvcc version, driver version. The
    operator pins which hardware class the baseline applies
    to.
- **Time:** 1.5 weeks.
- **Acceptance:**
  - Stub-deterministic kernel runs visualize correctly
    (5 runs → 1 unique hash → green).
  - Stub-non-deterministic runs visualize correctly
    (5 runs → 5 unique hashes → red).
  - Baseline-diff workflow lets operator accept or reject
    a hash-set change.

### Phase 8 — Accessibility + packaging + signing + UX test

- **Goal:** Production-grade ship.
- **Scope:**
  - **Accessibility:** WCAG 2.1 AA audit. Keyboard navigation
    every flow. Screen-reader compatibility (NVDA + VoiceOver
    + Orca minimum). Color-contrast pass. Reduced-motion
    respect.
  - **Internationalization:** at minimum English + Spanish
    (project author NANTAR AI ROBOTICS is Spanish-speaking;
    refineforge has Spanish-language users implicitly). All
    operator-facing strings via i18n bundle.
  - **Packaging:**
    - Windows: MSI installer signed with EV cert (or
      Sigstore-signed unsigned MSI for FOSS distribution).
    - macOS: signed + notarized .pkg + .dmg via Apple
      Developer cert.
    - Linux: AppImage + Flatpak + .deb + .rpm.
  - **Auto-update:** Tauri's built-in updater with signed
    update manifest hosted on a release server (GitHub
    Releases is the default; project's own CDN optional).
  - **Operator UX test:** 3 operators new to refineforge,
    each completing the 5-step task flow without help.
    Recorded sessions; >2 minutes per operator's average →
    fail and iterate.
  - **Criteria v0.4 review:** does the GUI's existence
    change the criteria? Likely a new Meta-rule: "operator
    actions taken via the GUI are equivalent to the same
    actions via CLI; the GUI does not introduce new
    categories."
- **Time:** 2 weeks.
- **Acceptance:**
  - All three operator UX tests succeed.
  - All packaging targets ship + auto-update works
    end-to-end.
  - WCAG 2.1 AA audit passes (independent reviewer).

## 5. Resource requirements

### People
- **1 senior engineer:** Rust + Tauri + Solid/React + Tailwind.
  Must know IPC patterns, async Rust, frontend build pipelines,
  + signed-package release rituals on three OSes.
- **1 designer (~10% time, 1.5 weeks total):** Figma, design
  system construction, accessibility audit.
- **1 reviewer (you, the operator, ~5% time):** UX validation,
  Phase 0 sign-off, Phase 8 final acceptance.

### Compute
- **Local development:** any modern laptop. macOS + Windows +
  Linux build VMs for cross-platform packaging (or GitHub
  Actions runners).
- **No GPU required** for the GUI itself.
- **Anthropic API:** ~$5-50 over the project lifetime for
  testing the Phase 3 live-streaming and Phase 5 repair-loop
  monitor.

### External services
- **Code signing certs:**
  - Apple Developer cert: $99/year.
  - Windows EV cert: $300-700 one-time + $50-200/year HSM
    rental, OR Sigstore-signed unsigned binary (free, requires
    operator to acknowledge SmartScreen warning on first run).
- **Auto-update server:** GitHub Releases (free) is the
  default; project's own CDN optional.
- **Error tracking (optional):** Sentry self-hosted (free) or
  Sentry SaaS ($26/mo). Opt-in only; never enabled by default.
- **Analytics:** none. Operator action telemetry is a no-go
  by design — refineforge is a trust tool and analytics would
  contradict the "operator decides" doctrine.

## 8. Out of scope (explicitly)

These DO NOT land in v1 even if useful:

- **Web-hosted SaaS version.** This is a desktop tool;
  offline-first. A SaaS layer would change the trust model
  (the operator's git is no longer the source of truth) —
  separate plan, separate threat model.
- **Built-in proof editor.** The operator writes Lean in
  their preferred editor (VS Code + Lean extension is the
  norm). The GUI opens files in the configured editor; it
  does not author Lean.
- **Plugin marketplace.** Overengineering. Refineforge's
  workflow is opinionated; plugins fragment it.
- **Mobile app.** Lean proofs aren't authored on mobile.
- **Real-time collaboration.** Multi-operator simultaneous
  editing of escalation packets is a v2+ feature; v1
  assumes one operator at a time per repo.
- **AI-tuned escalation criteria via GUI.** Criteria are
  human-edited only, per the criteria-doc itself.
- **Autonomous TRAINING runs with real GPU spend.** The
  trainer dashboard visualizes; it does not authorize real
  GPU billing without an operator-approved budget cap.

## 9. Open questions for the operator BEFORE Phase 0

These must be resolved before the project starts:

1. **Tauri 2.x vs Iced.** Tauri (recommended): desktop-app
   feel via system WebView, web stack for UI, smaller team
   ramp-up. Iced: pure Rust, no WebView dep, smaller
   community. Which fits the project's posture?
2. **English-only first, or English + Spanish from v1?**
   Spanish at v1 adds ~1 week to Phase 8; deferring is
   risky for a Spanish-authored project.
3. **OS priority.** All three (Windows + macOS + Linux) from
   v1, OR Windows + Linux first with macOS deferred?
4. **Cost-spend integration depth.** GUI shows upfront
   estimate + token counts (already in `RunReport`); does
   it ALSO need real-time Anthropic invoice integration
   (pulling from Anthropic's billing API), or is the
   estimate sufficient for v1?
5. **Crate placement.** New workspace member
   `crates/refineforge-studio` under the same repo, OR a
   separate `refineforge-gui` repo? Trade-off: same-repo
   means atomic releases + shared CI; separate-repo means
   independent versioning + smaller commit churn.
6. **Code-signing strategy.** Apple Developer cert + Windows
   EV cert (~$500/year), OR Sigstore-signed FOSS distribution
   (free; operator accepts SmartScreen warning on first run)?

Decisions go into a v0 of `docs/gui-plan.md` (this doc)
BEFORE Phase 0.

## 10. Failure-mode rehearsal (red team)

Before claiming the project succeeded, walk through each:

- **The "feature parity" failure mode.** What does it look
  like when operators demand every CLI flag be exposed in
  the GUI? Detection: feature-request count per release;
  alert if >10/month for >2 months. Response: hold the
  "CLI is canonical" line; add a "View as CLI command"
  toggle if needed.
- **The "trust drift" failure mode.** What does it look like
  when the GUI starts doing things the CLI can't? Detection:
  per-feature audit — every GUI capability must map to a CLI
  sequence; CI test fails if it can't be expressed. Response:
  refactor to surface the missing CLI commands first, then
  expose via GUI.
- **The "abandoned operator" failure mode.** What does it
  look like when the GUI's auto-update fails and operators
  are stuck on a stale binary? Detection: telemetry of
  binary version OR explicit version check at startup +
  warning if >6 months old. Response: in-app warning;
  manual update instructions in docs.
- **The "supply chain compromise" failure mode.** What does
  it look like when an attacker ships a poisoned GUI update?
  Detection: Sigstore signature mismatch on auto-update.
  Response: auto-update halts; in-app warning; manual
  intervention required.

## After v1: what next

With v1 shipped, the natural v1.1+ features:

- **Multi-claim batch operations.** Approve packets across
  multiple claims in one UI flow.
- **Claim-relationship graph.** Visualize which claims cite
  which theorems, identify high-blast-radius theorem changes
  before they land.
- **Plugin API for custom dashboards.** Operator-authored
  panels for project-specific metrics.
- **Cross-machine packet sync.** Multi-operator workflows
  via git remote — the GUI handles fetch/push of escalation
  packet commits automatically.
- **Mobile companion app.** Read-only escalation queue +
  approve-from-phone via signed git commits (HARD; requires
  rethinking the doctrine "operator decides on the same
  machine as the driver").

None of those are in v1's scope. Each is a separate multi-week
engagement after the GUI lands.
